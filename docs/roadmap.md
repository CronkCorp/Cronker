# Roadmap

Cronker is a fresh, simpler rewrite of Cronk (`CronkCorp/Cronk`), built to dogfood quickly and grow later. Vocabulary follows `CONTEXT.md`; hard-to-reverse decisions are in `docs/adr/`. The old Cronk's code, glossary and ADRs are a reference to copy from, not a constraint: where this file or an ADR here says otherwise, this repo wins.

## Settled

Choices from the initial grilling (2026-11-18) that are not ADRs but should not be reopened without reason.

### Foundation

- **Stack.** TypeScript, Fastify, Postgres, Docker Compose, as in the old Cronk; nothing may assume Docker.
- **Workspaces.** One installation holds several Workspaces (ADR 0002). Nothing crosses Workspaces; inside one, Projects are open or private with Read or Write Access, and Agent Access caps Agents (ADR 0010). Projects sit inside a Workspace, and Workspace knowledge layers under Project knowledge.
- **Users.** Sign in with GitHub or with an email and password. A User exists only once added to a Workspace; the first User is created at server setup. Any User may create a Workspace and becomes its Admin. An Admin adds people by GitHub login, or by email with a one-time link to set a password. There is no role above Admin; server commands handle recovery.
- **Reachability.** Cronk takes its public HTTPS address from configuration: a tunnel (Cloudflare Tunnel, Tailscale Funnel, ngrok) in development, a server in real use. Cloud Runs, Managed Agents webhooks and GitHub webhooks all need to reach it.

### Runs

- **Cronk launches Runs** (ADR 0001) through a narrow Runner seam: start a Run with this Brief, model and Repository; tell me when it ends.
- **Runners are per User**, with that User's credentials, so a Run spends the credentials of its Agent's Owner. Each Runner has its own limit on Runs at once (default 2, set by its User); Tickets beyond it wait, highest Priority first.
- **Subscription Runner** (first): Claude Code on the web scheduled tasks fired by API. The model, Repository and connectors are fixed on each task in claude.ai, so a User creates one task per model (for example triage on Haiku, investigate on Sonnet, implement on Opus) and gives Cronk each task's trigger under the model label its Steps use, optionally overridden per Project. A **Runner setup** does this for a Project from the Runner's card: the User's own Claude Code creates the routines, with the model ids the Workspace maps the labels to, and reports their trigger ids back, each waiting for the token the User pastes (ADR 0009). A rate limit pauses the Runner's queue until claude.ai's `Retry-After`. Cronk sends the Brief as the fire text, never a secret. The session reaches Cronk through a claude.ai connector authenticated by OAuth.
- **Managed Agents Runner** (second): the User pastes an Anthropic API key and Cronk creates one agent definition (Cronk's MCP server, default tools, tools allowed without asking) and one cloud environment in that User's Anthropic workspace. Each Run is a session of that agent with the Step's model as its override.
  - **Repositories.** A session mounts every Repository its Project lists, with a GitHub App installation token that Cronk rotates on the session about every 50 minutes while the Run runs; whether Managed Agents accepts App tokens is proven by its first ticket.
  - **Cronk's MCP token** is fresh per Run, held in an Anthropic vault the session names, and revoked when the Run ends (one vault per Agent with a lasting token is the fallback if per-Run credentials can't be made). The Brief never carries it.
  - **Ends.** A webhook is optional: the Runner's setup shows the webhook URL to add in the Anthropic Console and takes its `whsec_` signing secret. Cronk also polls sessions with running Runs every few minutes, since Anthropic drops a delivery after three tries. A session that goes idle without `finish` (whatever its stop reason), terminates, or asks for a confirmation fails the Run with that reason; lost Runs are as for any Runner.
  - **Stopping** a Run sends the session `user.interrupt` and then archives it. A Run that ends has its events fetched into its Transcript and its session archived, never deleted, so its Console link keeps working.
  - **Budget.** A Runner may set a *budget per Run* (empty by default), passed as the session's dollar budget; a Run stopped by it fails with *budget reached*.
- **Later Runners**: Agent SDK in a rented sandbox (E2B, Daytona, Modal and the like) or on a User's own machine.
- **Cloud or not.** Each kind of Runner says whether it runs in the cloud; both built-in kinds do. A Ticket labelled `local-only` is refused delegation to an Agent on a cloud Runner, and a Run that would start through one anyway is refused, saying why. An Agent with no Runner isn't cloud.
- **Agents.** Each User has one or more Agents with tokens. A Run acts as an Agent; so does Claude Code connected by hand. There are no Agent Sessions or Claims: a running Run holds its Ticket.
- **Run end.** A Run finishes when the agent calls `finish` with an Outcome. A Runner that reports the session ended without it makes the Run failed; a Run with no Cronk calls for a set time (default 30 minutes) is lost. Lost is Cronk's guess that the session is gone: a call by its Agent naming the Run or its Ticket brings it back to running, so a late `finish` is accepted, as long as it is still the Ticket's latest Run and nothing has moved on (the Ticket is still in its Status, still delegated to its Agent, with no other Run running). Failed and lost Runs wait in the Inbox with Retry; nothing retries on its own, except that pasting the token into a subscription Runner's trigger waiting for it starts the Tickets that couldn't start for want of it.
- **Brief.** Cronk's fixed preamble (how to reach Cronk, the Run's id, call `finish`), then the Step's Markdown brief (per Project, prefilled from Cronk's defaults), then the Ticket key. The agent reads the Ticket, Comments and Reports over MCP. A Project's **Concise Reports** setting (off by default) adds a rule to the preamble asking Runs to keep their Reports short; nothing stored is cut.
- **Cost.** Each Run records what it cost where the Runner reports it (Managed Agents sessions do; subscription Runs don't). It shows on the Run in the Ticket's timeline, totalled per Ticket, and per Runner for the month on the Runners page.

### The loop

- **The board is the pipeline** (ADR 0003). A default board: `Backlog → Triage [Haiku] → Ready → Investigate [Sonnet] → Implement [Opus] → Code review [Sonnet] → Merge [Haiku] → In Review → Done` (Merge from milestone 3).
- **Outcomes.** A Step lists named Outcomes, each with a target Status, including a *needs you* Outcome. A Run moves its Ticket only by an Outcome. Outcomes that send work back count as rounds; past the Step's round limit (default 2) they go to *needs you*.
- **Label rules.** A Step may require a Label or be skipped by one; a skipped Step passes the Ticket on by its default Outcome. The default Code review Step is skipped by `no-review`, which the triage Step may add to obvious cases such as docs-only fixes.
- **Delegation.** Only delegated Tickets get Runs. Delegating defaults to the delegating User's own Agent and assigns them if the Ticket has no Assignee. A Project sets whether new Tickets start delegated (off by default).
- **Autonomous Delegation and Verification** as in the old Cronk: set per Ticket, defaulting from the Project, inherited by Sub-Tickets; only then may an Outcome lead to Done, and the completion is Unverified until a User Accepts or Reopens it. Unverified counts as finished for blocking; Reopen sends the Ticket back to the Step that completed it.
- **Status kinds.** Backlog, Active, Review, Done, Canceled; at least one of each per Project. Agents never enter Canceled, and Done only under Autonomous Delegation. Done and Canceled Statuses never have a Step, so no Run starts on finished or canceled work; a Status with a Step can't become either kind until its Step is removed. On the default board, Backlog and Ready are Backlog; Triage, Investigate, Implement, Code review and Merge are Active; In Review is Review; Done is Done; and a Canceled Status of kind Canceled sits last.
- **Removing a Status** is refused while it holds Tickets, naming how many; they are moved out first. Removing never moves or deletes a Ticket, and renaming, moving or changing a Status's kind leaves its Tickets in it.
- **Agents change the board** over MCP (`read_project`, `add_status`, `edit_status`, `remove_status`, `set_step`, `remove_step`) by the HTTP API's routes and rules, with Write in the Project (the least of its Agent Access, the Owner's Access and the token's). Giving a Status a Step or changing one also needs the Agent's Owner to be an Admin, since a Step's Brief, model and Outcomes are what later Runs work by; taking a Step off needs only Write. Users need Write too.
- **Agents create Projects** over MCP (`create_project`) by the HTTP API's route, only when their Owner is an Admin and with a token that isn't read-only, since a new Project brings the default Steps. The Project gets the default board, starts open with Agent Access Write, and the Agent then changes it with the board tools. Any User of the Workspace may create one.
- **Questions** end a Run with *needs you*; answering one moves the Ticket back to the asking Step's Status, starting a new Run. Runs never wait.
- **Agents creating Tickets.** A Run may split its Ticket into Sub-Tickets, which inherit the Delegation; a parent gets no Runs while a Sub-Ticket is unfinished. Any other Ticket an agent files is a Discovered Ticket: Backlog, undelegated, assigned to the source Ticket's Assignee, in their Inbox until they delegate, move or dismiss it.
- **Inbox** per User: Questions, *needs you* Outcomes, failed and lost Runs, Unverified completions, Tickets in a Review Status, Discovered Tickets; none from an archived Project. No shared Triage view.
- **Leaving a Workspace.** Removing a User stops their Agents' Runs there and unassigns and undelegates their Tickets, which go to the Admins' Inbox, and removes their webhooks there.
- **Webhooks** per User and Workspace carry what waits in their Inbox to ntfy, n8n, Discord, Home Assistant or their own receiver: signed JSON deliveries laid out like Standard Webhooks, the kinds each chose, **Send test** and the last 20 deliveries on Account settings. Deliveries are kept in Postgres and sent by a check the server runs every five seconds. Only `https` URLs, except plain `http` to localhost on a local Cronk. Agents never see them. Each item in a User's own Inbox reaches their webhooks that chose its kind once, identified by its kind and source: a notifier on the live event bus reads the Inbox of each webhook's owner after changes, and on startup. A webhook that is off, or new, doesn't get what was already waiting. Retrying failed deliveries follows (Spec: Reach).
- **Removing an Agent.** Its Owner's removal undelegates each Ticket delegated to it, recorded as their Change; the Tickets keep their Assignee and Status. Its running Runs stop, as on any undelegation, and no Run ever starts for a removed Agent.

### Tickets

- Key `<PROJECT KEY>-<n>`, title, Markdown description, Status, Priority, Labels, Assignee, Delegate, Autonomous Delegation, parent, blocks and relates-to Relations, Linked Documents, Attachments, due date and estimate. No custom fields for now.
- Comments, and a timeline of Changes and Runs.

### GitHub

- **One GitHub App per installation**, created at setup through GitHub's manifest flow: sign-in, Repository access and webhooks. A Project lists Repositories the App is installed on; several Projects may share one.
- **Upgrading an existing App.** The manifest flow can't change an App, so an App created for sign-in alone is upgraded by hand: the GitHub page lists the permissions, events and webhook URL the App needs, links to its settings on GitHub, and shows what GitHub says it still lacks. New installations get everything from the manifest. Milestone 3 adds `contents: write` and `pull_requests: write` in one upgrade, for Managed Agents Runs to push and open Pull Requests and for merges by agents (ADR 0007).
- **Repositories on a Project.** Any User of the Workspace adds or removes them, choosing among the Repositories the App is installed on; installing the App on GitHub is the gate.
- **Missed webhooks.** GitHub doesn't retry, so on startup and every few minutes Cronk asks GitHub for the App's failed webhook deliveries and has them redelivered (GitHub keeps them three days). Nothing replays a longer outage.
- **Agents see Pull Requests.** Reading a Ticket over MCP includes its linked Pull Requests, their state, and the failing checks or requested changes that sent it back, so a Run sent back for another round pushes to the open Pull Request's branch instead of opening another; the default Implement brief says so.
- **Pull Requests** link to Tickets by key in branch or title, looking only at Projects that list the Pull Request's Repository. A User can also link one by hand, from the Ticket, when its branch or title doesn't name the key (CRONK-40): only an open or merged Pull Request Cronk knows, of a Repository the Ticket's Project lists. It then counts like a link by key, so its merge completes the Ticket, though a merge before the link completes nothing. A link by hand is kept apart from one by key: deliveries never remove it, and unlinking it, which only a User does, leaves a link by key standing. Projects sharing a key there all get the link. Keys are unique within a Workspace, so such Projects are always in different Workspaces: the Repository's settings in each warn that a Project of another Workspace shares its key there, never naming that Project or its Workspace.
- **A merge by a User** of the Ticket's Workspace, on GitHub or by Cronk for a Ticket they queued in the Merge Queue, completes every Ticket the Pull Request links that isn't already Done or Canceled, as Verified, moving it to its Project's first Done Status. A merge by anyone else (a GitHub account with no User in that Workspace, auto-merge, a merge queue) completes it the same way but Unverified, so it waits in its Assignee's Inbox. The first merge counts, so a Ticket's other Pull Requests don't matter, except that Cronk's merge of one of several Pull Requests a Ticket has in the Merge Queue waits for the last of them; unfinished Sub-Tickets don't hold it back; a running Run on it is stopped as if the User had moved the Ticket.
- **The Merge Queue** (ADR 0011): a User with Write presses **Merge** on a Ticket in a Review Status with an open linked Pull Request, in a Project with Pull Request automation on and a Merge Status; each of its open Pull Requests joins the queue for its own Repository and base branch and the Ticket moves into Merge. A periodic pass merges each queue's head once it is clean and green, one per queue at a time in the order they joined, as that User's merge; the Ticket's last queued Pull Request merging completes it as Verified, and leaving Merge takes all of its entries out. A head that isn't ready yet waits. An Autonomous Delegation Ticket in a Project with *agents may merge* and Pull Request automation on joins on its own as it enters Merge (CRONK-95), recorded as Cronk's Change; Cronk merges it as its Agent's, with no Run, completing it as Unverified. Turning *agents may merge* off passes the Tickets only Autonomous Delegation queued on to In Review and keeps those a User queued. A head GitHub says is behind its base branch but merges cleanly has its branch updated through GitHub's update-branch (*Updating branch*), then waits, holding its queue, for the new commit's checks to go green (*Waiting for checks*) before it merges; check, status, check suite and review deliveries for a queued Pull Request have the queue act on it at once. **Remove from queue** sends the Ticket back to its first Review Status, and a Pull Request merged or closed on GitHub leaves its queue. A failing check on its latest commit or a review requesting changes, at the head or waiting, takes a queued Ticket out of the queue and sends it back to the Step that produced its Pull Request as a round, with Cronk's Comment, or, with no producing Step, to its first Review Status, not as a round. A merge GitHub refuses (branch protection, required approvals, a ruleset, GitHub's own merge queue) takes it out by the Merge Step's *needs you* Outcome, Cronk's Question quoting GitHub's reason. Either way the next Ticket moves up, and a Ticket with several Pull Requests leaves every queue at once. A head GitHub says conflicts with its base branch steps aside, out of line, so the queue moves on (CRONK-98): Cronk writes a Comment naming the merge that caused it and a Run of the Merge Step starts (*Resolving conflict*), whatever the Step's rule, to resolve the conflicting hunks and push to the Pull Request's branch. Its *resolved* Outcome leaves the Ticket in Merge until the resolution's checks are green (*Waiting for checks*), then it rejoins its queue at the front; a failing check sends it back as a round. Sending it back to Implement from that Run counts as no round. Each entry steps aside at most 3 times: a fourth conflict, or a Ticket with no Delegate or a Merge Step without *resolved*, takes it out by *needs you* with Cronk's Question. `read_ticket` shows the entry and the conflict that last set it aside. Existing Projects' Merge Steps gain *resolved*; their Briefs stay their own.
- **A merge by an agent** (milestone 3) completes the Ticket as Unverified. Agents merge only through the Merge Queue, which Cronk merges as the Agent's, or Cronk's `merge_pull_request` tool, which a Project's own Merge Brief may still use (Cronk merges with the App token, recording the Agent and Run), and only on Autonomous Delegation Tickets in Projects with *agents may merge* on (off by default); as a safety net, a merge by a User's account while that Ticket has a running Run counts as the agent's.
- **The Merge Step** (ADR 0005, amended by ADR 0011) sits on its own Status, between Code review and In Review, and skips itself, passing the Ticket on to In Review by its default Outcome, unless the Ticket may be merged by an agent or a User queued it in the **Merge Queue**, which merges it with no Run. A Ticket an agent may merge joins the queue as it enters; it gets a Run only when it has no open Pull Request to queue, and the default Brief has that Run find out why and send it back or ask, merging nothing. With Pull Request automation off it skips. A Project's own Brief may still merge with `merge_pull_request`, which uses the Repository's default merge method and refuses unless the Pull Request is linked to the Run's Ticket, GitHub says it is mergeable, its checks are green with none pending, and no review still requests changes. A merge completes the Ticket as Unverified and finishes the Run with *merged*, without `finish`. A conflict at the head of the queue starts a Merge Run that resolves the conflicting hunks, pushes to the Pull Request's branch and finishes *resolved*; a resolution that isn't mechanical goes back to Implement by *send back*, its Comment saying why.
- Failing checks or requested changes on a Ticket in a Review Status, or queued in the Merge Queue, send it back to the Step that produced the Pull Request, with a Comment linking the failure; this counts as a round. One already known on the latest commit, or a review still requesting changes, when an Outcome moves the Ticket into a Review Status sends it back then, unless it sent the Ticket back before. The producing Step is that of the Run running on the Ticket when the Pull Request opened, by the time GitHub gives for its opening, so a delivery arriving after that Run finished still finds it; a Pull Request opened with no Run running (by a User) sends nothing back. A failing check is any check run, commit status or check suite on the Pull Request's latest commit ending failed, timed out or cancelled (or, for a check run or suite, failing to start), required or not, so a workflow that fails before it runs any job still counts; requested changes are any *changes requested* review, whoever wrote it.
- **Merge conflicts** mark a Ticket's Pull Request instead of sending the Ticket back: GitHub's answer that it conflicts is kept against the Pull Request, with the base commit and the merge that made it conflict, and shows as a *Conflicts with `<base>`* marker on the Ticket's board card and its Pull Requests, with no Comment, Change or round, until a later answer that it merges cleanly clears it. GitHub sends no event when a Pull Request becomes conflicting, so Cronk asks: when it sees a merge into a Repository, for the other open Pull Requests on that base branch whose Tickets are in a Review Status, asking again shortly while GitHub is still working mergeability out; when an Outcome moves a Ticket into a Review Status; and after a push to a marked Pull Request, which may resolve it. An Outcome into a Review Status still sends a Ticket back for a failing check or a review requesting changes Cronk already knows. Nothing is asked in a Project with Pull Request automation off. Direct pushes to a base branch aren't watched for now (that would need the `push` event).
- A Pull Request opening or becoming ready doesn't move Tickets; Outcomes do. A Project can turn Pull Request automation off: merges then complete nothing and failing checks or requested changes send nothing back, but Pull Requests still link to and show on their Tickets.

### Knowledge

- **Documents** in a page tree per Project and Workspace, with Versions; a save based on an outdated Version is refused. Users edit them in a rich editor that stores Markdown, with a toggle to its Markdown source (built for every place Users write Markdown: Documents, Decisions, Terms, Ticket descriptions, Comments, answers and Step Briefs), where Mentions show as links while writing and a picker offers the Tickets, Decisions and Terms a key or a Term's first letters may start. **Reports** are Documents a Run writes on its Ticket, listed with the Ticket instead of in a page tree; milestone 1's separate Reports move into Documents, gaining Versions and Attachments. A Ticket may link a Document of its Project or of the Workspace.
- **Attachments** are stored as files in a directory set in Cronk's configuration (a volume under Docker), so a backup is the database plus that directory. The size limit per file is configurable, 25 MB by default. Agents add Attachments over MCP to anything they may write. Markdown refers to an Attachment through a reference Cronk resolves (`attachment:…`), so images keep working wherever the text moves.
- **Terms and Decisions** as typed records per Project and Workspace, Project Terms replacing Workspace Terms of the same name, exported as `GLOSSARY.md` and `docs/adr/`. Agents create and edit Terms and propose Decisions; only Users change a Decision's status. No Protected items or Suggestions.
- **Export** is a download from the Project or the Workspace, and the same files over the API and MCP, so a Run writes them into its own branch; Cronk never commits to a Repository. A Project's `GLOSSARY.md` holds the Workspace's Terms with the Project's on top; its `docs/adr/` holds only its own Decisions. The Workspace's export holds the Workspace's.
- **Decisions** are numbered in order of creation, separately per Project and for the Workspace, and the export's file names carry the number (`0005-…`). *Superseded* names the Decision that replaces it, in the same Project, or both in the Workspace, so no export names a Decision it lacks. An accepted Decision's text stays editable, with Versions; only its status is limited to Users.
- **Artifacts** with Versions, isolated by the browser sandbox on Cronk's own hostname (ADR 0004); the optional second hostname comes later.
  - An Artifact is a page plus supporting files (scripts, styles, images, data) that it refers to by relative paths, versioned together and stored in the Attachments directory, with a title and a description. The Attachments size limit applies to a Version's files in all; `attachment:` references don't work inside the sandbox. A save based on an outdated Version is refused.
  - Every sandbox response, for every Version, also carries a content security policy, so a page an agent wrote can't send what it shows anywhere: `default-src 'none'`; scripts and styles from its own files (`'self'`, Cronk's own address, which holds under the sandbox's opaque origin), inline code, cdnjs, jsDelivr, unpkg and Google Fonts (with `fonts.gstatic.com`); images, media and fonts from those, `data:` and `blob:`; `connect-src 'self'`; no frames, form submits or base changes. Since the page's origin is opaque, its own `fetch` of a file is cross-origin, so sandbox responses carry `Access-Control-Allow-Origin: *` without credentials; the key stays the only guard of a Version, as before. The tool descriptions tell agents to bundle data as files. The policy doesn't stop a page navigating itself elsewhere; the sandbox's lack of `allow-popups` and `allow-top-navigation` limits that to its own frame or tab.
  - Each Version is served under its own unguessable key (`/sandbox/<key>/<path>`) that needs no sign-in: the sandboxed page's own requests carry no `SameSite=Strict` cookie, so its files can't be guarded by one. The API hands the address only to those who can read the Artifact.
  - Owned by a Project or the Workspace, each listed by last change. One made during a Run (the Agent names its running Run) is linked to its Ticket; Users link and unlink others as with Linked Documents. Only a User deletes one, with its Versions and their files.
  - Its page shows it in a sandboxed iframe, with its Versions and a per-file text diff between two. Agents use `create_artifact`, `save_artifact`, `read_artifact` and `list_artifacts`, with the same routes on the API.
- **Transcripts** (ADR 0006) are converted from either source into one list of entries (role, text, tool name and input, tool result, time) in Postgres. A long tool input (as JSON) or tool result is cut at 20 KB, a Transcript past 50 MB keeps its start and end with the gap marked (a last message over 25 MB alone is cut at 20 KB to be its end), and known secret patterns (Cronk's tokens, GitHub's, Anthropic's, AWS access keys, Slack's, private-key blocks, bearer values) become `[scrubbed]` before anything is stored. Kept forever; any User of the Workspace may delete one (Agents can't), for when the scrubbing missed a secret. A deleted Transcript's Run says it was deleted, and later uploads of its session are refused so nothing comes back.
  - **Managed Agents Runs:** Cronk fetches the session's events when the Run ends, and the newer ones whenever someone opens a running Run's Transcript.
  - **The Transcript hook**, for subscription Runs and hand-connected Claude Code, is a script Cronk serves. The Runner's page shows the `settings.json` snippet to commit in each Repository and the setup steps, with a dedicated *Transcript hook* Agent token for the cloud environment. It uploads the whole transcript on every `Stop`, and Cronk replaces what it holds for that session. It finds its Run by `CLAUDE_CODE_REMOTE_SESSION_ID`, which matches the session id the fire returned; claude.ai names one session both `cse_…` and `session_…`, and Cronk keeps both as `cse_…`, so either finds the Run. Every upload counts as a call naming that Run, and for long turns the snippet also runs the hook on `PostToolUse`, where it only tells Cronk the Run is alive, at most once every 5 minutes, so a Run whose session is working never becomes lost. It never fails the agent's turn: errors go to stderr and it exits 0. Repository hooks run only in one-Repository cloud sessions, and the environment must reach Cronk (Full network access, or Cronk on the Limited allowlist).
  - **Hand-connected Claude Code** sessions have no Run: their Transcripts belong to the Agent, listed on its page, and link to every Ticket their Cronk tool calls name. A Run's Transcript follows its Ticket's Project; a hand-connected one is shown only to its Agent's Owner, Admins and Users who can read every Ticket it names (one naming none only to the Owner and Admins), and among Agents only to its own.
  - Every Run keeps its session link; its timeline entry links its Transcript, a page showing messages in full and tool calls collapsed to a line, following new uploads of its session live.
- **Search.** Postgres full-text across Tickets, Documents, Reports, Terms and Decisions; Artifacts by title and description; Transcripts, by an entry whose text has the whole search, ranked below the rest. No AI service required. The `english` configuration with web-search syntax (`"phrase"`, `or`, `-word`), results with highlighted snippets. The web client has a search box in the sidebar frame opening a results page grouped by kind, across the Workspace with a Project filter; agents get `search(query, project?, kinds?)` over MCP. Results the viewer can't read are left out, before each kind's cap, and so are an archived Project's unless the Project filter names it.

### Interfaces

- One documented HTTP API; the UI and the MCP server are its clients. MCP takes OAuth (claude.ai connectors; the consent screen picks one of the User's Agents) and bearer tokens.
- Live updates over server-sent events for the board, the Inbox and Run states.

## Milestones

1. **The loop.** *Built.* Sign-in, Workspaces, Projects, Admins, Agents and tokens; Tickets with all kept fields; the board with Status kinds, Steps, Briefs, Outcomes, round limits and Label rules; Delegation, Autonomous Delegation, Verification, Questions, the Inbox, Reports, live updates; the HTTP API and MCP with OAuth; the subscription Runner with Run states and limits. Dogfooding starts here: `docs/setup.md` sets an installation up.
2. **Code and knowledge.** *Built.* Code first: the GitHub App upgrade, Repositories on Projects, Pull Requests, merges by Users, failures sending work back. Then knowledge: Reports into Documents, Documents with Versions, Linked Documents, Attachments, Terms and Decisions with export. Last, a styling pass over every screen, milestone 1's and 2's alike, following `docs/ui.md` (adapted from the old Cronk's): first the foundation (design tokens, IBM Plex faces, the shared components, the sidebar frame), then each screen.
3. **More Runners and the rest.** *Built.* Transcripts first: their storage and view, filled by the Transcript hook. Then the Managed Agents Runner, filling them from fetched events. Then merges by agents with the Merge Step, search, and Artifacts.

## After milestone 3

Ideas, not yet grilled.

- **Hosted skills.** Skills (a `SKILL.md` plus files, with Versions) kept per Workspace and Project in Cronk and edited in the web client. They reach Runs natively on the Managed Agents Runner, and over MCP (listed in the Brief, with a `read_skill` tool) on the others, hand-connected Claude Code included. A `SessionStart` hook installing them into `.claude/skills/` could follow once it is proven. They may replace the old Cronk's Guidance: a skill marked as always loaded does Guidance's job.

## Not now

Custom fields, Protected items and Suggestions, full Markdown export and import, Workspace-wide webhooks, email, a shared Triage view, other Git hosts.
