# Testing

Tests exercise Cronk from the outside, the way a User or Agent does: they call the HTTP API (or drive the web client) and assert on responses and on what later calls return. They never read tables, import internal modules or call private functions (the rich editor's round trip and state, seam 8, are the one module the web client offers as a seam), so the inside can be refactored freely. Only the harness reaches in, and only for what starting Cronk takes: `createCronk` and the migrations that build its template database. The one exception is a test of a migration that moves data an earlier Cronk wrote: it writes those rows as that Cronk did (`stage()`, below), since today's API can no longer write them, and reads the result through the API. Rules are not tested through lower-level unit seams.

## Seams

These are the seams from the milestone 1 spec (#1). Tests live only at them.

1. **HTTP API against a real, disposable Postgres** (primary). Cronk runs in-process with the clock under the test's control, keeping Attachments in a disposable directory. Nearly every rule is tested here, live updates included, by reading a Workspace's event stream over HTTP. Lives in `test/api/`, the readable forms the API takes in place of ids among them (`test/api/readable-forms.test.ts`), the OpenAPI document served with a few sentinel routes (`test/api/openapi.test.ts`), and the event stream (`test/api/live.test.ts`: its security cases one by one, and one parametrised case per resource the stream tells about), and Mentions (`test/api/mentions.test.ts`: each kind of text linking its Ticket keys and listed under Mentioned in, what isn't a Mention, Access, and indexing the texts written before the Mention index on the next start). A resource's plain refusals (another Workspace's member or Agent, an Agent where only a User may act, a read-only token, a missing field or Version, an unknown id) sit together in one table-style test per resource, each case checked for its status and error and the whole checked for having changed nothing.
2. **The Runner interface with a fake Runner.** Every `startCronk()` installs a fake Runner (`test/harness/runner.ts`) as the Runner kind `fake`. It records each start and stop and can be told to refuse the next start (rate limits included) or to report a Run ended without finishing. Agents' own calls, such as `finish`, come through the API or MCP. Lives in `test/api/runs.test.ts`, `test/api/runs-gone-wrong.test.ts`, `test/api/delegation.test.ts`, `test/api/agent-work.test.ts` (what an Agent does inside its Run: edits, Reports and its last call), `test/api/reports.test.ts` (Reports as Documents, and milestone 1's moved over), `test/api/agents-creating-tickets.test.ts` (Sub-Tickets and Discovered Tickets an Agent files, edits and blocks, and their settling in the Inbox; where a case meets a Relation rule it checks the rule holds through an Agent's routes), `test/api/runner-events.test.ts` (a Runner's Owner hearing of Runs starting and ending on it, of its pause and resume, and of its removal) `test/api/leaving.test.ts` (an Admin removing a User from a Workspace) `test/api/transcripts.test.ts` (Transcripts uploaded by an Agent: converted, scrubbed and capped, replaced on a second upload, and matched to the Run whose session they record, and, for a session of no Run, listed on its Agent and linked to the Tickets its Cronk tool calls name, telling the Workspace's streams of each upload, and deleted by a User but never by an Agent) and `test/api/transcript-hook.test.ts` (the Transcript hook Cronk serves, run as a child process through the `settings.json` snippet's commands with a sample hook input, a JSONL file and Cronk's address and token: its upload becoming the Run's Transcript, a failed upload said on stderr with exit code 0, and its uploads and `PostToolUse` pings, at most once every 5 minutes, keeping the Run from becoming lost).
3. **The subscription Runner against a stand-in HTTP server** for the scheduled-task fire endpoint. Every `startCronk()` points Cronk at a stand-in (`test/harness/claude.ts`); the real service is never called. Lives in `test/api/subscription-runner.test.ts`, and a Runner setup (the command and plan, the served instructions, reporting back, triggers waiting for their tokens, and the Workspace's model ids) in `test/api/runner-setup.test.ts`, whose Claude Code half is simulated by fetching the instructions and reporting back over HTTP.
4. **The Managed Agents Runner against a stand-in Managed Agents API.** Every `startCronk()` points Cronk at a stand-in (`test/harness/managed-agents.ts`) for agents, environments, vaults and their credentials, sessions with their events, Repository resources, interrupts and archives; the real service is never called. Lives in `test/api/managed-agents-runner.test.ts` (setting up with a key, rejected keys, starting a session with its Step's model, its Brief, a vault of its own and its Project's Repositories, rotating their installation tokens, `finish`, stopping, lost Runs, polling, cost and the budget per Run, rate limits, removing the Runner, its webhook: saving the signing secret, and signed, forged, stale, repeated and unknown-session deliveries, and the Run's Transcript filled from its session's events: converted, scrubbed and capped when the Run ends, fetched page by page, and appended to since the last fetch when someone opens it while the Run runs).
5. **MCP** (thin): a real MCP client (the MCP SDK's) against the running server, for bearer tokens (a missing or revoked one refused), OAuth and the mapping of tools onto the API: the tool list, a refusal reaching the Agent with its code, rule and advice, and one test per tool family (Tickets, search, Comments, `finish` and merging, edits and Reports in a Run, linked Documents and Artifacts, attachments as base64 and their refusals, Sub-Tickets and Discovered Tickets, a Project's Statuses and Steps, Documents and their Sections, Terms, Decisions, Artifacts and export), each naming some things by their readable forms. The rules stay with the API tests. Lives in `test/mcp/`; the OAuth flow's rules (consent, codes, refresh, Client ID Metadata Documents) are tested at the API in `test/api/oauth.test.ts`, with one Playwright walk through the consent screen in `e2e/connect.spec.ts`. A test publishes a client's metadata document from its own local HTTP server: a Cronk on plain http, which only a local one may be, accepts plain http metadata document URLs.
6. **GitHub against a stand-in GitHub.** Every `startCronk()` points Cronk at a stand-in GitHub (`test/harness/github.ts`) for the manifest flow, OAuth sign-in, account lookups, the App's own calls with its JWT (what it has, its webhook, its installations), installation tokens, the repositories an installation covers (listed, or one by id, as after a rename), and the App's signed webhook deliveries with their log and redeliveries; the real GitHub is never called. Sign-in and creating the App live in `test/api/github.test.ts`, linking a GitHub account to a User who signs in with a password in `test/api/github-link.test.ts`, upgrading the App, installations and their tokens in `test/api/github-app.test.ts`, webhooks in `test/api/github-webhooks.test.ts`, Repositories on Projects (renames and transfers, and key clashes across Workspaces) in `test/api/repositories.test.ts`, Pull Requests linking to Tickets with their state, checks, review state and producing Step, merges completing their Tickets, and failing checks and requested changes sending them back (Pull Request automation included), in `test/api/pull-requests.test.ts`, a Merge Run merging its Ticket's Pull Request through `merge_pull_request` (its refusals, the merge method and token, and the completion) in `test/api/agent-merges.test.ts`, merge conflicts sending them back, found by asking GitHub for a Pull Request's mergeability, in `test/api/merge-conflicts.test.ts`; `e2e/main-path.spec.ts` walks the GitHub path once in a browser. A test sends `pull_request`, `pull_request_review`, `check_run`, `check_suite` and `status` deliveries with only the fields Cronk reads.
7. **Web UI smoke tests** (Playwright): a few walk the main path in a real browser. The web client holds no rules, so it gets no further tests: a rule shown on a page is tested at the API, and the look is checked by review and the screenshots `docs/ui.md` asks for. A Playwright test earns its place only for what a browser alone can show: the main path wired end to end, or a mechanism the API can't see (dragging, keys, a sandboxed iframe, dropped files, a live stream reconnecting). They run in Chromium; those tagged `@every-browser` run in Firefox and WebKit too, since browsers differ in dragging. These are all of them, and a new one replaces or joins one of them only with that reason:
   - `e2e/main-path.spec.ts` walks the whole of it with the fake Runner and the stand-in GitHub, from setup through the Merge Step's Run merging the Pull Request, moving the card to Done, to Accepting that Unverified completion; `e2e/smoke.spec.ts` sets up a fresh installation without GitHub, signs in and out.
   - `e2e/connect.spec.ts`: the OAuth consent screen connecting a claude.ai connector.
   - `e2e/tickets.spec.ts`: creating Tickets, dragging one across the board, editing, commenting, a key link and filtering.
   - `e2e/board.spec.ts` (`@every-browser`): a card dragged onto another column, onto its own and refused, from anywhere on it (its link, Labels, avatars and empty space), and to the board's edges; and, in Chromium only, **Group Sub-Tickets** folding Sub-Tickets into their parent's card, or into a copy of it in their own column when the parent is in another, unfolding them there and being remembered on this browser, since the folding is done by the web client and the API can't see it.
   - `e2e/card-menu.spec.ts`: a card's menu by keyboard, Move to starting a Run as a drop does.
   - `e2e/read-access.spec.ts`: an Admin making a Project private and listing a User with Read, whose board offers no New Ticket and whose cards neither drag nor open their menu, and whose Ticket and Document show rendered text with no rich editor where the Admin's Document still has one, while another User doesn't see the Project.
   - `e2e/board-selection.spec.ts`: several cards selected by Ctrl/Cmd+click, Shift+click, Space and Shift+Space, Escape clearing them, a selection dragged and moved with Move to, and its refused moves listed per Ticket.
   - `e2e/comments.spec.ts`: `C` reaching the Comment box of a long Ticket, never while typing or with a modifier, and Ctrl+Enter placing a Comment from the rich editor and from its Markdown source.
   - `e2e/inbox-keys.spec.ts`: the Inbox's keys.
   - `e2e/live.spec.ts`: the board and a Ticket following another member's change, and the Live indicator turning to Reconnecting… and back; with it, Cronk stopping at once while a browser holds an idle or in-flight connection.
   - `e2e/attachments.spec.ts`: files dropped or pasted on a Ticket.
   - `e2e/artifacts.spec.ts`: an Artifact in its sandboxed iframe and opened directly, its scripts running but unable to read Cronk's cookies or call its API.
   - `e2e/mentions.spec.ts`: a Ticket key in a Document linking to its Ticket, which lists the Document under **Mentioned in**, the link worked out by the web client from what the API returns.
   - `e2e/transcripts.spec.ts`: a Run's Transcript opened from its timeline, following a new upload, a tool call expanded, and deleted.
   - `e2e/search.spec.ts`: searching from the sidebar, results grouped by kind, the Project filter and opening a result.
   - `e2e/addresses.spec.ts`: a Ticket at its key's address, any letter case replaced by the canonical one.
   - `e2e/editor.spec.ts`: the rich editor on a Document: its toolbar, keys and Markdown shortcuts, the source toggle both ways and remembered on this browser, its toolbar as one stop with arrow keys between its buttons, and, at a wide window, text that fills the frame so long lines wrap at its edge with their line breaks kept through save and reload.
   - `e2e/documents.spec.ts`: files pasted or dropped into the rich editor's text, each an Attachment shown where it went in.
   - `e2e/scope-switch.spec.ts`: the knowledge pages' scope dropdown by keyboard, each choice an address that Back and Forward move between.
   - `e2e/frame.spec.ts`: the sidebar, and at phone width a strip with the rest in a menu.
   - `e2e/styling.spec.ts`: the faces loading from Cronk itself, and every colour the stylesheets set coming from a token.
8. **The rich editor's round trip** (component): Markdown in, the editor's document, Markdown out, through `openMarkdown` (`web/src/editor/round-trip.ts`), the shared editor's one seam, which takes Markdown and gives Markdown back. ProseMirror runs without a browser, so this needs no DOM and no Cronk. Edits are ProseMirror transactions, as the editor makes them. Lives in `test/editor/round-trip.test.ts`, over the handwritten samples in `test/editor/samples/` (`attachment:` references, Mentions, Embeds, tables and task lists, code blocks, raw HTML and footnotes, nested lists, odd spacing, Windows line endings) and this repository's own Markdown docs: each comes back byte for byte without edits and with only the touched block changed after an edit to any one block, Markdown the editor can't show is a source block kept as written, and the source mode goes through the same round trip. `test/editor/state.test.ts` opens the same samples through `openDraft` and `markdownOf` (`web/src/editor/state.ts`), the state the shared component edits, with all its plugins, and drives its toolbar's commands, its Markdown shortcuts as typed, pasting and an Attachment's reference, checking the Markdown each saves. Playwright walks the component on a Document in `e2e/editor.spec.ts` and `e2e/documents.spec.ts` (seam 7).

What a seam can't see, such as that only hashes of secrets are stored, is kept by code review rather than by tests reaching past the seam.

## The harness

`test/harness/` holds what every test starts from:

- **`startCronk()`** (`start-cronk.ts`) creates a disposable database, starts Cronk in-process listening on a free local port, and returns the following. Cronk's public address names its port before it listens, so the harness picks the port first; when another test takes it in between, it starts Cronk again on another, as `upgrade()` does. `start-cronk.test.ts` checks the harness itself: many Cronks started or upgraded at once each answer at their own `url`.
  - `url`: Cronk's address, which is also its configured public address, so the browser and `Origin` checks see the same thing.
  - `github`: the stand-in GitHub Cronk talks to (below).
  - `claude`: the stand-in claude.ai fire endpoint (`claude.ts`) the built-in `subscription` Runner fires scheduled tasks at. `claude.trigger(id, token)` adds a trigger it knows (others answer 404, a wrong token 401), `claude.rateLimitNext(retryAfter)` answers the next fire with 429, and `claude.fires` lists every fire with its trigger id, token, headers and body.
  - `managedAgents`: the stand-in Managed Agents API (`managed-agents.ts`) the built-in `managed_agents` Runner calls. `managedAgents.apiKey(key)` adds a key it accepts (others answer 401); `agents`, `environments`, `vaults` (each with its `credentials`, a second for the same MCP server URL in one vault answering 409, as Anthropic does) and `sessions` list what was created, each with the request's body; `session(id)` reads one (its status, events, its `resources` with the token each holds now, and whether it was archived or deleted), `idle(id, stopReason)` and `terminate(id)` move it on as Anthropic would (`idle(id, "budget_reached")` as its budget stops it), `charge(id, cents)` adds to what it reports in `usage.list_cost`, `emit(id, ...events)` records the agent's work as session events (`agent.message`, `agent.mcp_tool_use`, …), `pageSize(n)` lists at most `n` events a page, a `user.interrupt` sent to a running session makes it idle, `rateLimitNext(retryAfter)` answers the next request with 429, `failNext(method, path, status)` answers the next request to that path with that status, as an outage would, and `calls` lists every request it answered, with its query. An archived agent is marked `archived`. `webhookSecret()` makes a `whsec_` signing secret as the Console does, and `deliver(url, { secret, type, sessionId, at, id })` sends a thin webhook event about a session to a Runner's webhook URL, signed as Anthropic signs it (Standard Webhooks headers), at the test clock's time it is given; sending an `id` again is a retry.
  - `runner`: the fake Runner (`runner.ts`). A User sets up a Runner of the kind `fake` (`POST /api/runners`) and points an Agent at it; `runner.starts` lists every start asked of it, `runner.stops` every stop, `runner.refuseNext(refusal)` refuses the next start, and `runner.endWithoutFinishing(runId)` reports a Run ended without finishing.
  - `checkForLostRuns()`: runs the check the server runs every minute, which makes lost the Runs nothing has named for their Workspace's lost-Run threshold. Move the clock first.
  - `pollManagedAgentsSessions()`: runs the check the server runs every three minutes, which reads the sessions of running Managed Agents Runs and fails those whose sessions went idle without `finish`, asked for a confirmation or terminated, then lets go of what ended Runs still hold where Anthropic didn't take it before: deleting their vaults, archiving their sessions and fetching their last events into their Transcripts.
  - `rotateRepositoryTokens()`: runs another check the server runs every minute, which sets a fresh installation token on each Repository resource of a running Managed Agents Run's session whose token expires within ten minutes. Move the clock first.
  - `resumePausedRunners()`: runs another check the server runs every minute, which resumes the queues of rate-limited Runners whose pause has passed. Move the clock first.
  - `replayFailedDeliveries()`: runs the check the server runs on startup and every five minutes, which has the stand-in GitHub redeliver the App's failed webhook deliveries Cronk hasn't applied.
  - `checkMergeability()`: runs the check the server runs every five seconds, which asks GitHub about the Pull Requests a merge or an Outcome into a Review Status left waiting on a mergeability check, sending a conflicting one's Tickets back. One GitHub is still working out is asked again ten seconds later: move the clock first.
  - `request(method, path, { body, cookie, origin, headers })`: a `fetch` against it. It sends no `Origin` unless asked, like a non-browser client.
  - `clock`: the test's clock (below).
  - `logs` and `setupCode()`: everything Cronk logged, and the setup code a fresh installation logs.
  - `attachmentFiles()`: the files in the disposable directory this Cronk keeps Attachments in, by name (each an Attachment's id), to check that a removed Attachment's file is gone. `startCronk({ attachmentLimitBytes })` sets the size limit of each Attachment (25 MB by default).
  - `terminateIdleDatabaseConnections()`: terminates Cronk's idle database connections from an admin connection, as a Postgres restart or failover would, and returns how many it terminated.
  - `stage(sql, params)` and `upgrade()`, for a test of a migration: `startCronk({ migrateBefore: "0022_reports_documents.sql" })` starts Cronk on a database migrated short of that migration (no template, so it pays for its migrations); the test sets things up through the API, stages with `stage()` the rows only an earlier Cronk wrote, then `upgrade()` restarts Cronk, on a new address (`url` follows it), applying the rest. When today's API needs a later migration the one under test doesn't depend on to set the test up, such as the columns creating a Project writes, `applyAhead(name)` applies it first and records it, so `upgrade()` skips it. `test/api/reports.test.ts` moves milestone 1's Reports into Documents this way, and `test/api/pull-requests.test.ts` marks the send-back Comments Cronk wrote before the mark existed.
  - `command(...args)`: runs a server command (`server/command.ts`) in a child process against this Cronk's database, as an operator would, and returns its exit code, stdout and stderr.
  - `stop()`: closes Cronk, drops its database and removes its Attachments' directory. Call it in `afterEach`; stopping it again does nothing, as when the next test's `startCronk()` failed and `afterEach` still holds this one.
- **Disposable Postgres per test** (`database.ts`). Each `startCronk()` copies a fresh database from a migrated template (`create database … template …`), so tests share nothing and none pays for migrations. The template's name carries a hash of `migrations/`, so changing a migration builds a new template on the next run.
- **The injectable clock** (`clock.ts`). Cronk reads the time only through its `Clock`. `TestClock` starts at a fixed instant and moves only on `clock.advance(ms)`; `days(n)`, `hours(n)`, `minutes(n)` and `seconds(n)` help. Use it for anything that expires.
- **The stand-in GitHub** (`github.ts`). A local HTTP server answering as GitHub does, redirects included, for creating a GitHub App from a manifest, authorizing it to sign in (OAuth), looking up accounts, and the App's API calls. `github.account(login, email?)` adds an account GitHub knows of; `github.signedInAs` is the account the browser is signed in to GitHub as, who approves at once; `github.apps` lists the Apps created, each with the `permissions`, `events`, `webhookUrl` and `webhookSecret` its manifest asked for, which a test edits as an Admin would in the App's settings. `github.install(app, account, repositories)` installs an App, accepting its permissions at that moment; an installation keeps them until `installation.accept()`. `github.tokensIssued` lists every installation token issued; tokens last an hour by the test's clock. `github.pullRequest(repository, number, fields)` adds or changes a Pull Request as GitHub's API answers about it (its head commit, open, draft or merged, and `mergeable`: true, false as with a conflict, or null while GitHub works it out; its base branch and the base commit GitHub compared against, `main` and `b0` by default; and `answers`, what each ask answers in turn instead, the last staying, alone or against another base commit), which the App may merge with an installation token; `github.merges` lists each merge it made, with its method, the head commit it named and the installation whose token asked. `github.onMerge` runs once GitHub has made a merge, before it answers, as when GitHub's delivery of the merge reaches Cronk first. A repository's `mergeMethods` says which merge methods its settings allow, all by default. `github.deliver(app, event, payload, { id, secret })` sends a webhook delivery to the App's webhook URL, signed with its secret (another, or `null` for none) and returns Cronk's answer; sending an `id` again is a redelivery. `fails: "unreachable"` stages a delivery that never reached Cronk, `fails: "timed out"` one Cronk got but GitHub gave up waiting for; either is logged as failed. `github.deliveries` is each App's delivery log, which the App lists and asks redeliveries from, `github.redeliveries(app)` the attempts it asked for, and `github.refuseNextRedelivery()` answers the next redelivery request with 422, and while `github.unavailable` is true its API answers every call with 503. `github.apiCalls` lists every API call it answered, as `METHOD /path`, to count what Cronk asks, such as none for an installations list it keeps. It checks the App's JWT against its key and the test's clock. Cronk starts with a random `CRONK_SECRET_KEY`, or none with `startCronk({ noSecretKey: true })`.
- **`openStream(cronk, cookie, workspaceId)`** (`stream.ts`) opens a Workspace's event stream as any client would and resolves once the server has subscribed it; `openRunnerStream(cronk, cookie)` opens the signed-in User's own Runners' stream the same way. `next()` waits for the next event, `expectQuiet()` fails if one arrives, `ended()` waits for the server to end the stream, and `close()` drops it; `stop()` ends any still open.
- **`unzip(archive)`** (`zip.ts`) reads a zip archive, such as an export's download, into its files by path, as any unzip tool would.
- **Flows** (`flows.ts`): `setUp(cronk)`, `signIn(cronk)` and `addMember(cronk, adminCookie, workspaceId, email)` (added by email, joined through the link, signed in) for tests whose subject comes after them; `createGitHubApp(cronk, adminCookie)` and `signInWithGitHub(cronk, account)`, which follows the browser's redirects between Cronk and GitHub. Keep them few; a test about setup or sign-in itself spells the requests out.

Faults and external services are staged through the harness, never by mocking Cronk's own modules: the stand-in GitHub, the stand-in fire endpoint, the stand-in Managed Agents API and the fake Runner are four; later tickets add more stand-in HTTP servers as `startCronk` options.

## Writing a test

```ts
let cronk: StartedCronk;
beforeEach(async () => { cronk = await startCronk(); });
afterEach(async () => { await cronk?.stop(); });

test("a sign-in lasts 30 days", async () => {
  await setUp(cronk);
  const cookie = await signIn(cronk);
  cronk.clock.advance(days(30));
  expect((await cronk.request("GET", "/api/me", { cookie })).status).toBe(401);
});
```

Name tests after the behaviour, in `CONTEXT.md`'s vocabulary. Expected values come from the spec or a worked example, never recomputed the way the code computes them.

## Running tests

The tests need a Postgres server (16 or later) they may create and drop databases on. They connect to `CRONK_TEST_DATABASE_URL`, by default `postgres://postgres:postgres@localhost:5432/postgres`. Any Postgres works, for example:

```sh
docker run -d --name cronk-test-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16-alpine
```

Then:

| Command | Runs |
| --- | --- |
| `npm run typecheck` | The type checker over the server, web client and tests |
| `npm test` | The API tests (Vitest) |
| `npx vitest run test/api/sign-in.test.ts` | One test file |
| `npx vitest run test/mcp` | The MCP tests |
| `npm run test:e2e` | Builds the web client, then the Playwright smoke tests. The first time, install the browsers with `npx playwright install chromium firefox webkit` |

Test databases are dropped when each test stops; templates (`cronk_template_*`) are kept for the next run and can be dropped at any time.
